# Single validation and trusted accepted data

The user explicitly requires one admission check, followed by trust in the accepted value in memory or storage. This policy applies to the complete product and supersedes earlier requirements for repeated schema, byte-hash, content, catalogue or definition consistency checks on accepted data.

New user/provider/import input passes one admission step at its owning entrypoint. That step checks the shape and substantive conditions needed to use it: a generated clean script contains the requested roles and no planned mutations; a new mutation output provides usable mistakes and locations; an answer mapping supports scoring; newly uploaded bytes satisfy their declared input metadata. The application stores the accepted value and reuses it. A new model reply, edited request, imported file or replacement version is new input and gets its own admission step.

Reads, ordinary use, checkpointing and Resume trust accepted documents, linked blobs, saved configuration, frozen prompt bundles and completed model results. They do not re-run schemas, recompute hashes to reject delivery, replay content validation or consult current definitions to qualify old data. Decoding stored JSON or reading fields is ordinary data access. A genuinely missing record, inaccessible blob or failed database call reports the actual dependency error. It does not fabricate data.

Freeze the request, settings, selected models/voices, prompts/context and application data needed to resume. Keep IDs, revisions and existing hashes as provenance and routing metadata. Do not retain a separate archive of schema files or adapter source code, require byte-equivalent definitions after upgrades, or add definition/correspondence audits. Current supported adapters consume the saved settings. An actually unavailable adapter or provider reports its capability error. Optional Lab retains actual prompts/context/model outputs and quality measurements, rather than a second copy of the application implementation.

Readiness observes database/media/speech availability. Initialization owns migration admission and private-bucket setup. Ordinary health requests do not audit migration history, column types, trigger functions or the full schema catalogue. Existing accepted database data/configuration is trusted. The operation that actually uses a missing column or resource reports its own dependency failure.

Keep operation idempotency, revision compare-and-swap, deadlines and active-owner arbitration: these decide which action may commit. Keep explicit provider selection and the included/free/local billing policy; spending still requires the user's individual approval. Keep the exact42 scoring formulas, all122 categories/recipes, all11 optional source scopes, text/mutation/audio/answer flows and LLM development features. Those are product behavior, not repeated data qualification.

The first acceptance of staged bytes after interrupted upload can check the staged object because it has no committed admission record yet. Once marked accepted, upload retry, Verify, link, playback and Resume use that accepted record without another byte audit or synthetic provider call. Database foreign keys and ordinary atomic writes associate records; routine writes do not rescan the complete historical graph. A new parent-reference submission may validate its newly introduced path once.

Tests use independently expected input/output/state/arithmetic to establish these behaviors, including that accepted reads and reuse work without the removed checks. Historical observations of the superseded policy remain historical. Workflow DAG/source receipts describe development evidence; they do not install runtime validation ceremonies.
