# Persistent preparation and explicit resume

Preparation uses the existing PostgreSQL typed documents/entity heads, private assets and foreground operation records. It adds no queue, scheduler, accounts or new service. preparation-state.schema.json owns the durable association; preparation-settings.schema.json owns the frozen private snapshot. These contracts apply to ordinary authored generation. Imported/native rendering remains supported with preparation_id=null.

Before the first generate call, create a preparation UUID and the original operation record. Persist the complete normalized request/expanded blueprint, configuration, exact selected source_record_ids, resolved canonical/mutation bindings, exact prompt bundle and selected speech/recipe registry bytes. Secrets are references, never values. Serialize settings assets as those exact UTF-8 JCS bytes; the asset byte hash and settings_sha256 therefore agree. Retain the selected prompt/context payload and settings needed for Resume. Accepted data is trusted under single-validation-policy.md; no schema/adapter archive is required. Link the saved settings asset and preparation-state in one transaction before dispatch. settings_sha256 is SHA-256 of UTF-8 RFC8785 JCS of the complete settings payload; registry hashes cover their actual saved bytes. Asset storage/readback follows runtime-and-storage.md. A failed snapshot write dispatches no call.

The state always has canonical_text, mutation and render phase states. canonical complete requires canonical_asset_id/canonical_sha256; mutation complete requires candidate_id, mutated_asset_id and mutation_manifest_asset_id; render complete requires linked audio_asset_id/audio_sha256 and saved key_id. Other outputs remain null until they actually exist. A persisted render plan can precede successful audio. The canonical hash uses the unchanged generation-contract-details.md candidate projection. Remaining asset IDs select their already accepted payload through asset records; saved hashes are provenance metadata. The preparation record itself has no self-digest; document.payload_sha256 covers its full canonical JSON.

Each checkpoint transaction links the accepted phase assets, appends actual receipts, advances the preparation head revision and records its phase state together. A completed clean-text checkpoint commits before mutation dispatch. A completed mutation checkpoint commits before rendering. Earlier completed phases remain complete on later failure; last_failure preserves the actual error. Failed/partial outputs and orphan reservations remain separate actual operation evidence, not reusable completed checkpoints.

The running foreground operation owns writes through active_operation_id and the existing operation deadline. A checkpoint write compares the preparation head revision, exact active_operation_id, nonexpired deadline and target phase. No database transaction spans a model call. A late superseded/deadline-expired operation is retained as diagnostic evidence and cannot replace selected checkpoints. A process crash leaves its actual operation/partial assets; after its deadline, the next explicit continuation marks that phase interrupted and acquires a fresh foreground operation identity. No additional permission epoch or recovery worker exists.

Readback: GET /api/v1/preparations lists saved preparation-state records, including incomplete/failed ones, ordered by created_at then id, using the existing page/limit convention. GET operation status and the existing preparation view include the associated preparation record. These reads dispatch zero model/speech calls. UI Preparation shows the original topic, phase statuses, saved completion/failure and Resume, using the saved request display; it never substitutes current settings. The settings asset is private operational context, not a listener key projection or public credential body.

Generate request with preparation_id=null starts a new preparation. Non-null selects that exact record; blueprint_id, effective_configuration_sha256 and source_record_ids must match the saved snapshot. generation_attempt is the actual next explicit operation counter. Repeated action idempotency returns the already committed result; a fresh explicit continuation uses a new Idempotency-Key. Its generation work starts at the first incomplete phase: completed canonical bytes are reused, completed mutation returns the saved candidate without inference. There is no blueprint-only search for the latest baseline. A changed request/profile/prompt/voice/recipe selection is New exercise with a new preparation ID; it cannot alter a selected checkpoint.

Render request for an authored exercise supplies its preparation_id. The submitted plan matches the saved candidate and frozen blueprint/selected speech definition. Persist the plan before the actual call; later explicit retries reuse that same plan. A changed plan/voice/backend is a new explicit rendering/preparation version, not Resume. Do not require the currently active global profile/bundle to match the old one: use the saved binding and prompt/context payload directly. A secret value can be corrected at its same local credential reference; it is never part of the content snapshot. An unavailable old adapter/binding reports the actual configuration error and preserves all artifacts; no provider substitution occurs.

Rendering recovery reuses the existing reservation/upload/admission/link protocol: if complete bytes are already accepted, finish linking those bytes without another audit rather than buy synthesis again. Partial/refused/incomplete provider output is not a completed checkpoint. A link committed before response loss is returned on readback/idempotency lookup. Playback uses the final linked audio, not a preparation promise. Backup includes every preparation/settings/checkpoint/reference and restores their exact association. Explicit cleanup/deletion handles these references under the existing maintenance procedure; browser/process restart never erases the preparation.

Concrete sequence: preparation p1 freezes model M1, prompt bundle B1, speech S1 and clean asset c1. Mutation times out. Global settings change to M2/B2/S2. After restart, p1 still reads c1 and M1/B1/S1. Resume invokes only the incomplete mutation phase and later renders with S1. New exercise creates p2 with M2/B2/S2. A fourth explicit failed-render retry is permitted; each operation still has its own 270-second deadline and bounded automatic requests. This is written behavior, not observed persistence.

Resume on an already complete preparation reads/returns its existing playable version with zero provider calls. A response-lost but committed mutation is read back before render; a response-lost committed render is read back as complete. An explicit Re-render/New exercise action is distinct from Resume and creates the declared new rendering/preparation version; it cannot replace previously frozen listening attempts.

Full-scope rendering extension: full-build-contract.md owns durable per-piece progress, completed-piece reuse,270s foreground continuation and restoration. New preparations explicitly persist render_progress_asset_id; partial overall phase does not invalidate a complete saved piece.

## Iteration5 implementation boundary

The native canonical stage now has an application owner, app.PrepareCanonical, using InvokeLLM and the packaged `prepare` maintenance entrypoint. Blueprint write/read and keyset preparation pages use the existing private HTTP server. The combined user-facing Generate action, mutation, rendering and teacher workflow remain later increments; the canonical stage never returns a falsely complete mutated/playable exercise.

Frozen settings retain the original blueprint, both generation bindings, prompt bundle/templates/context and selected application registry data. Reads and Resume trust accepted records. No schema/adapter definition archive or repeated byte/schema check exists.

Canonical completion stores the candidate's unchanged1.0.0 contract in a private accepted asset and atomically records the real word count, selected preparation head and owning operation. Failed phase/head/error receipts finalize together. A lost preparation checkpoint can recover only a completed matching child of that preparation's recorded operations; it does not search the latest blueprint or call the provider again. Native constructed-response tests exercise this storage/transport behavior. Actual hosted generation, linguistic quality and hosted MLflow evidence remain unobserved and blocked; full later-phase/product completion is not claimed.
