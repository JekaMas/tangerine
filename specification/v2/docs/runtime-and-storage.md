# Transactions, storage, and recovery

## Canonical identities

Generate object IDs with cryptographic UUIDv4 values. Do not put names, answers, or source content in object keys.
Use RFC 8785 JSON Canonicalization Scheme (JCS), encoded as UTF-8, for structured hash projections. Reject duplicate keys, unpaired surrogates, non-finite numbers and integers outside the interoperable safe-integer range unless the schema represents them as decimal strings. Generic key sorting is not an equivalent encoder. No Unicode normalization is applied by JCS.
Preserve original text bytes separately. Never normalize the saved answer before hashing it.
Hash canonical structured records with SHA-256. Store large exact numbers as the declared decimal strings.
Use only the exact hash projection for that record kind in `docs/persistence.md`. Do not apply a generic field exclusion list.
A content digest excludes mutable lifecycle state, revision counters, lease metadata, and audit timestamps.
The schema registry supplies the exact content projection for each versioned kind.

## Request identity

Each mutating request uses `Idempotency-Key`, a UUID generated by the browser for one intended action.
The database key is `(workspace_id, operation_name, idempotency_key)`, where operation_name is the stable domain/operations.yaml operation ID, not the per-request UUID. Hash a JCS object containing the operation name, normalized concrete path (including target), query parameters, If-Match revision or null, and parsed body (or exact binary-body SHA-256). A changed target, body, query or revision under the same key returns IDEMPOTENCY_CONFLICT. The original receipt remains immutable.
Store the canonical body hash, target revision, completion status, and result document reference.
The same key and body returns the original operation result. It does not call a provider again.
A different body or target with the same key returns 409 `IDEMPOTENCY_CONFLICT`.
An unfinished matching operation returns its saved state. It does not imply success.
The explicit retry endpoint uses a new request key and refers to the same frozen attempt.

## Database and object storage

Before an upload, commit an asset reservation and operation record together.
Use an opaque new object key. Never overwrite an existing object.
Write the bytes under that key. Finish a multipart upload before further checks.
Read the complete stored object and calculate its size and SHA-256.
A length or digest mismatch marks the reservation failed. It cannot become linked.
In one database transaction, lock the reservation and owning version.
Make sure that the operation, expected revision and digest match.
Set the asset to `linked`, add exact ownership references, update the owner, and append the audit event.
Media delivery requires the linked state and available actual bytes; source-use notices remain visible.
The audio hash identifies final WAV bytes, not an upstream stream or a provider promise.

| Crash boundary | Recovery on an explicit recovery request |
|---|---|
| Reservation only | Show an incomplete upload. Erase it only under an explicit local cleanup plan. |
| Partial upload | Abort its exact multipart upload. Retain the failed operation receipt. |
| Bytes exist, no verified digest | Read and hash those same bytes. Do not call synthesis again. |
| Verified bytes, no database link | Reapply all current guards and attempt the link once. |
| Link committed, response lost | Return the committed identity through idempotency lookup. |
| Owner revision changed | Keep the asset unavailable as an orphan. Do not attach it to the new version. |
| Source notice changed | Report the changed notice; explicit local cleanup follows the selected plan. |

Garbage collection is an explicit maintenance operation. It presents the exact asset IDs and bytes before confirmation.
Referenced assets are ineligible. Backup manifests and immutable history count as references until their retention permits removal.

## Evaluation lease

Submission first commits the exact answer, answer digest, case version, final audio digest, policy digests, and server time.
The attempt's start time comes from the database transaction that creates the attempt.
The evaluation lease stores a random token, an increasing epoch, its owner request, and a 300-second expiry.
The end-to-end evaluation deadline is 270 seconds from lease acquisition.
Every stage write compares attempt revision, token, epoch, deadline and current case status in one transaction.
A stale writer cannot publish a result even if its provider call returns successfully.
No transaction remains open while an external call executes.

An active lease returns 409 `EVALUATION_ACTIVE` with a safe result lookup path.
After lease expiry, explicit retry increments the epoch and starts a new deadline.
The previous answer, case, audio, and policy remain frozen.
A profile change creates a separate explicit reconsideration operation, not a retry disguised as the original evaluation.

## Stage reuse

Reuse only a completed stage whose full cache identity matches.
Store source-use restrictions/revocation notices as metadata; normal operations use local settings, with no permission-epoch or grant-closure service. Actual source terms and unknown observations remain visible.
Reapply local semantic checks to the stored output before reuse.
Do not reuse partial/refused or genuinely disputed output; a successfully repaired validated output is reusable under its exact binding.
Mapping audit is optional; disagreements are diagnostic. Genuine score-relevant uncertainty may use one LLM adjudication, never retries selected for favorable grades.

## Deadlines and transport attempts

Stage limits are extraction 40 seconds, mapping 70 seconds, audit 70 seconds, and feedback 40 seconds.
The request retains at least five seconds for persistence and return.
The effective stage timeout is the lesser of its stage cap and remaining request time minus that reserve.
There is at most one additional transport attempt across the whole evaluation request.
Retry only a connection failure before response bytes, HTTP 408, HTTP 429, or HTTP 502/503/504.
Retain refusal as refusal; allow one output repair for malformed/incomplete replies within the existing deadline, as defined in provider-contracts.md.
Use Retry-After only when it parses as a nonnegative delay and fits the remaining budget.
Without a usable Retry-After, wait one second. If the delay and minimum five-second call budget do not fit, stop.
Count each call in the usage ledger, including failed or uncertain-charge calls.
SDK retries must be disabled. Adapters cannot add another retry layer.

Cancellation or connection loss signals cancellation to the active call.
Commit the saved-answer/interrupted status before returning when the connection still permits a response.
A process crash leaves the lease to expire. Recovery requires an explicit action.
A complete provider output that arrives after deadline remains diagnostic evidence only.
The API timeout is 285 seconds, the proxy timeout 300 seconds, and the browser timeout 310 seconds.

## Input capacity

Do not truncate the answer, key, correction alternatives, evidence, or role instructions to fit a provider.
Use the shipped tokenizer for a documented model. For an unknown tokenizer, count UTF-8 bytes for all trusted instructions, serialized user DTOs, wire schema and protocol framing as a conservative local bound; include the reserved output budget. An unknown tokenizer uses the configured conservative bound; this is an input-size setting, not a separate qualification prerequisite. For local_responses gpt-oss:20b and gpt-oss:120b the offline embedded o200k_base ordinary-text counter is used (tiktoken-go v0.8.1); o200k_harmony shares those ordinary BPE ranks. Count the final serialized request once per new transport attempt, including any repair/fallback additions, and reserve max(4096, configured max_output_tokens). The snapshot records that actual counter identity, method, count and reservation. These counts measure serialized request text; provider-internal chat framing and provider-reported usage remain separate observations. Unknown provider/model pairs retain the conservative UTF-8 byte bound. Intermediate Lab context assembly does not apply a second byte rejection before the final provider serializer. Standalone Lab previews retain their explicitly conservative preview budget. No required family, taxonomy, recipe, original text or answer-key data is truncated to fit. References: [OpenAI tokenizer ranks](https://github.com/openai/tiktoken/blob/main/tiktoken_ext/openai_public.py), [offline Go counter](https://github.com/tiktoken-go/tokenizer).
The profile must declare a context capacity and an output reservation.
If input bound plus output reservation exceeds capacity, return `INPUT_CAPACITY` before the call.
An output that reaches a provider cap without complete status returns `OUTPUT_INCOMPLETE`.
Provider output normalization and one same-profile repair request are permitted as defined in provider-contracts.md; omitted source answer/evidence is never fabricated.

## Hash projections

Use the named content projection in `docs/persistence.md`. Do not remove every field named id or hash from an object.
A server envelope digest omits only its own digest field. A case content digest excludes review receipts to prevent a digest cycle.
Hash source files over the original bytes. Hash JSON domain content with RFC 8785 after schema validation.
A field containing a previously measured asset digest is part of the subject content. Do not omit it.

Current preparation persistence/resume is defined by preparation-persistence.md and preparation-state/preparation-settings schemas. Generation must be self-contained under self-contained-generation.md; no private contextual fact determines a scored mistake. Key repair uses key-repair-projection.md and the existing LLM operation. These are written contracts, not implemented behavior.

New private documents acoustic-production-plan,render-progress,source-mapping-program and audio-judge profile/input/output reuse existing typed documents/operation receipts and private MinIO. Render progress is linked by the PostgreSQL preparation head; full-build-contract.md specifies producer/readback/lifecycle and sample-map storage. No new background runtime or application identity is introduced.

Current admission/readiness/reuse policy: [single validation](single-validation-policy.md). Hashes are calculated as provenance at creation; accepted records and blobs are trusted afterward. No repeated readback, schema catalogue, trigger/type audit or implementation-definition archive is an ordinary runtime requirement.

The mutation request frame carries the full typed stage input once. When the selected blueprint, taxonomy, recipes, canonical script or public-context component is already identically present in that input, omit its redundant second message. Keep all trusted instructions, complete private component evidence and the full original DTO. Different/custom/unknown components remain separate messages, and other phases keep their existing frame. This serialization compaction never drops required data, changes the selected category set or adds an accepted-data audit.
