# Full product development and operation

The product scope is fixed for the complete implementation, not an MVP followed by deferred product features. Development may iterate on code, prompts, models, fixtures and repairs. Such iterations must preserve every accepted feature, all 122 category/recipe identities (114 error leaves and eight acceptable controls), all 42 original equations and all eleven original full-source scopes. Optional means the user selects a feature; it does not authorize omitting its implementation or calling missing source content complete.

The written specification is sufficient to begin full-scope development. It is not sufficient evidence that every feature can already operate with the available accounts and data. Whole-product acceptance includes main flow, all requested mutation realizations, diagnostics, source import/completeness, Lab, reports, persistence, backup/restore and local delivery. A playable ordinary exercise or a structural validation pass cannot stand for that acceptance.

The implementation/evidence map below supersedes the earlier research-only implementation-status wording. It preserves the original completion conditions. Current I16evidence belongs to audit/iteration-16-release-20261021; a selected software test cohort is not the entire historical property matrix or full external-source acquisition.

## Controlled local Kokoro phoneme contract

Official KPipeline.generate_from_tokens accepts raw engine phoneme strings; the upstream model vocabulary is finite. The original kokoro-local-en-v1 profile remains the plain-text baseline. A configured extension uses provider local_kokoro, adapter_version kokoro-phonemes-v1, local billing and frozen model/voice/tokenizer assets through speech-profile.schema.json. It uses the existing render-plan and speech-render-request/result; no new public endpoint or account is introduced. Only this implemented adapter may advertise ipa and word_stress. It does not advertise generic fine prosody or arbitrary IPA.

For a plain text operation, phonemize the exact saved surface wording with the selected US/GB Misaki pipeline. For a phoneme operation, use its explicit IPA for that occurrence only. Preserve target-unit/span association; an identical word elsewhere keeps its normal phones. NFC-normalize the requested phone string and apply the frozen longest-match conversion: tʃ→ʧ, dʒ→ʤ, eɪ→A, aɪ→I, ɔɪ→Y, aʊ→W, oʊ→O, əʊ→Q, ɝ→ɜɹ. Other characters pass through only when present in the actual frozen model vocabulary. Preserve lexical ˈ/ˌ and supported length markers as intent. Unsupported symbols retain the failed target and its reason; never let the model silently drop them. These conversions are an engineering binding, not a claim that a rhotic vowel/duration/accent was acoustically verified.

Build ordered token/phone spans retaining the original and compiled strings. Split into engine chunks of at most 510 phoneme characters at token boundaries before generate_from_tokens; keep an entire target span in one chunk. If a target itself cannot fit, return the existing constraint failure with the saved key, rather than truncate it. Do not split by a fixed number of text characters. Call the selected fixed voice and speed; save input/output/seed when actually supported. Insert explicit pauses locally on the final sample clock. Predicted durations are model predictions, not measured phone observations. Actual rendered audio, joins, hashes and intervals use the existing assembly/provenance contract. All acoustic acceptance tests use actual output; no pre-use certification ceremony is introduced.

Sources: [official pipeline API](https://github.com/hexgrad/kokoro/blob/main/kokoro/pipeline.py), [model configuration](https://huggingface.co/hexgrad/Kokoro-82M/blob/main/config.json), [Misaki English phonemizer](https://github.com/hexgrad/misaki/blob/main/misaki/en.py). Research inspected on 2026-10-09; implementation lockfiles must pin actual revisions/assets, not use a mutable main URL as a release identity.

## Local independent ASR contract

Method faster-whisper-local-en-v1 runs under the existing private Python speech owner with an explicitly downloaded multilingual small model converted for CTranslate2, frozen asset digests and dependency versions. Default device is cpu, compute_type int8. Use WhisperModel on the local model path, then transcribe the actual 16-kHz mono advisory derivative with language=en, task=transcribe, beam_size=5, temperature=0, word_timestamps=true, initial_prompt=null, condition_on_previous_text=false and vad_filter=false. Consume the returned generator completely before marking success. Never pass clean text, mutated text, the answer key or user answer as a transcription prompt. Save actual segment/word text, probabilities/timestamps and language metadata before comparison. Unknown tokens and ASR errors remain the hypothesis; do not silently replace them with the reference. Compute WER using the existing lexical-v1 policy, preserving raw timestamps and final-clock mapping. Missing model/runtime or incomplete output gives an unavailable diagnostic, never a fabricated zero WER. Include this method in explicit diagnostic model setup, not ordinary startup or a cloud fallback.

Invoke it through the existing speech_measure operation with measure-request.method_ids containing faster-whisper-local-en-v1, the exact case version and final audio hash. The resulting audio-measurement uses feature WER, unit ratio, final-clock interval and the saved raw ASR artifact in evidence_asset_ids; its decimal value represents the exact S+D+I divided by the reference-token count under lexical-v1. Missing or zero reference denominator gives not_measurable/null/reason. Raw segment/word objects, timing units and metadata remain in the private evidence artifact; original reference tokens are used only by the later WER computation. This is independent transcription, not Azure phoneme/prosody scoring and not a substitute for an audio-capable judge. Source: [official faster-whisper usage and word timestamps](https://github.com/SYSTRAN/faster-whisper).

## English voice locale and provider endpoint compatibility

Blueprint variety-policy defaults remain en-US/en-GB. A voice locale is independent of the assessed target variety and can be any configured English locale returned by the selected backend, including en-IN or en-AU. Render-plan and speech-render-request accept the English locale syntax; dispatch resolves it against the frozen selected profile/voice catalogue. They do not manufacture a voice for every accepted string. Accent descriptions stay separate, and an en-US variety policy does not force every speaker to have a US accent.

ElevenLabs v4/v3 use the documented POST /v1/text-to-dialogue route with one inputs entry for each separately rendered piece: text and voice_id, explicit model_id, language_code=en and supported pronunciation_dictionary_locators. Use mp3_44100_128, retain actual response receipts and assemble ordered turns locally. Do not send the TTS endpoint's voice_settings object on the dialogue route; only documented supported settings belong there. Keep total text at or below the documented reliable 2,000-character request size for that route and target-safe segmentation. Older supported single-voice models use /v1/text-to-speech/{voice_id}. Model-specific input limits and phoneme-dictionary support must come from the frozen adapter/catalogue contract; Flash v2 and Flash v2.5 are separate model IDs, not interchangeable aliases. An available model's can_do_text_to_speech flag alone does not establish which transport it accepts. Sources: [dialogue request](https://elevenlabs.io/docs/api-reference/text-to-dialogue/convert), [current model catalogue](https://elevenlabs.io/docs/overview/models).
